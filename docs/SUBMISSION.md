# 提交说明

## 优先解决的问题

旅客不一定知道航司规则，也不会一次给全信息。系统先澄清航司/票价/行程，再提供有来源的答案；涉及自己的客票时才要求身份。改签和取消先展示逐项费用，用户明确确认后才改变订单。网络中断不能被当作业务失败后再重复退款。

首版优先政策咨询、授权客票查询、改签和取消/退款。它们覆盖不同航司、边界资格、金额方向以及完整状态变化。新购机票、真实支付/航司接入和真正人工审批不在本次范围。

## 关键决定与取舍

1. 三份 PDF 用本地 FTS5 和审核快照；无需为有限资料引入向量数据库。检索证据与可执行规则分别版本化。
2. 模型负责意图、追问和工具选择；金额、UTC 时间、资格、授权和确认均由后端控制。未知不补猜，聊天里的“确认”不能提交资金操作。
3. 本地 SQLite 事务一起保存订单、库存、账本、额度与请求结果；防重键和客票版本处理重复提交与并发冲突。该保证不延伸到真实外部航司或支付系统。
4. 浏览器优先业务卡和明确状态；注册用户与虚构样例身份分开。多人和并发、账号、故障测试是扩展投入，核心评审可只走 README 的三个任务。
5. 本次托运行李输入支持三边合计，不猜单边尺寸；随身/客舱行李仍需按政策核对单边。原退改执行器保留字节指纹，已知旧版本只迁移当前规则关联，保留历史记录并使旧报价重新校验；其他未知代码版本仍拒绝启动。

## 如何评估

规则与接口测试核对金额/税费、时间、权限、并发、防重与恢复；浏览器测试核对实际页面和后端，使用受控模型；真实模型单独运行十个业务场景和八个自由表达场景。每例保存预期、实际、来源、工具与持久化状态。详细结果以 [VALIDATION](VALIDATION.md) 为准，未运行或失败不会写成通过。

## 限制与下一步

政策只来自给定虚构材料，资金不代表银行到账。后续新增的可选[M9服务试用](SERVICE_TRIAL.md)让注册用户可申请样例票、模拟客服可接单/补充/转办、旅客可查订单和退款进度、按预算与到达时间比较样例方案，并看到模拟航变提醒。它不提供真实人员、真实身份核验或外部回执。真实试用仍需确定出票渠道及服务责任，接入真实订单/退款和客服时限；复杂联程、额度兑换、支付补偿与通知仍未完成。见 [业务缺口](BUSINESS_GAPS.md)。

## 实际投入

原题上限为六小时。本项目未按该上限交付，开发和复核记录横跨2026年9月18日至20日；没有可核实的人工计时，无法给出精确人工小时数。以上包含多轮功能扩展、缺陷修复和自动化等待，不能换算成同等人工时长。AI 工具参与设计、开发和验证；提交者应能解释取舍、复现证据并现场修改。
