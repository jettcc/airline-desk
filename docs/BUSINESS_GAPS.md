# 真实业务试用前的缺口

这是基于当前实现的产品分析，不是对真实航司规则或生产合规的认证。作业仍只使用给定的三份虚构政策。2026-09-20已将其中一部分做成可选的[M9本地服务试用](SERVICE_TRIAL.md)：样例核验、模拟客服队列、渠道结果跟进、受约束方案比较和站内航变动态。以下区分可演示的工作流与仍然缺少的真实接入。

## 首先明确服务责任

真实产品需要先确定运营者是航空公司、出票平台，还是只提供咨询的第三方。目前的演示将三家航司和模拟订单放在同一后台，尚未解决真实渠道之间的办理权和责任归属。建议首轮试用限定为一个出票渠道、明确可办理的航司和票种；外部渠道订单提供经过核验的转办路径。不能因为能解释政策就暗示有权替旅客改票或退款。

## 按旅客是否能完成事情排序

| 优先级 | 真实旅客场景 | 当前已有 | 仍缺少的闭环 / 下一步 | 如何验收 |
|---|---|---|---|---|
| P0 | 注册后找回自己或代办人的真实客票 | 本地账户；注册用户样票核验申请、独立角色批准、逐票动作授权、到期/撤销；公开演示码不是真实核验 | 真实订单关系核验、真实委托与员工身份、出票渠道授权和核验失败后的可用转办路径 | 本人能找回授权订单；陌生人、付款人自述不能取得权限；需要核验时有可完成的流程 |
| P0 | 取消成功后追问“钱什么时候到账” | 原子账本与跟进任务；订单/退款分开；模拟完成/失败/未知与查询原请求、凭证、防重 | 上游请求与签名回执、支付资金来源、真实退款对账、异常补偿和到账时限；模拟回执不能代替银行完成 | 外部成功回执丢失、退款延迟或失败时不重复执行，能说明阶段和下一步，最终有可核对的完成凭证 |
| P0 | 部分已用、医疗或权属问题需要人工 | 模拟工作台接单、补充信息、转办、回复/拒绝；责任角色与时间线；未知金额不批准 | 真实人员与审批权限、处理时限/超时升级、材料安全入口、核定规则和经过审批的恢复办理 | 用户无需重复讲述；申请从待处理走到有依据的结果；没人接单或超时有升级路径 |
| P0 | 航班再次变化或座位已无，原方案不能用 | 逐票模拟航变、保留原时间、版本复核、旧报价拒绝、站内提醒与重新选择 | 真实航班/客票同步、同航班全部旅客事件投递、连续航变、可靠上游回执、外部通知 | 变化后用户能知道哪项改变、可选什么；不悄悄加价或用旧行程声称完成 |
| P1 | “明早必须到，尽量少补钱，别拆散同行人” | 样例库按最终到达UTC/最高总补款筛选完整同行方案，显示费用后另行报价确认 | 真实库存、机场最短衔接时间、复杂联程、个性化服务/行李和退款方式偏好、多航司方案 | 候选满足显式硬约束，列明取舍；无满足条件的方案时说明原因，不仅列航班让用户自行推算 |
| P1 | 多次改签、跨渠道、联程或混合支付订单 | 部分使用边界、原出票时间、逐段税费、本人额度核对 | 真实票价规则与渠道/航段/承运关系匹配；混合支付资金来源；额度兑换/余额/到期提醒；额外服务后续处理 | 不能把三份通用政策套到不适用订单；金额来源不明时保留未知并可转办；服务和资金去向逐项可追踪 |
| P1 | 不方便长聊、出发临近或多次求助的旅客 | 核验/查询/补充说明/比较可通过结构化界面操作，已有记录跨会话查询；原聊天中英文/时区 | 出发紧迫性与队列优先级、实时提醒、跨渠道连续服务、真实行程凭证；试用界面英文尚未实现 | 少重复输入；模型不可用时仍可查已有结果和进入可用的人工渠道；不会把已登记说成已解决 |

## 首轮试用看什么

除了回答正确率，还需分别统计：适用范围内任务完成率、无依据金额/资格回答数、错误或重复办理数、用户重复补充同一条件的次数、人工接单和解决时间、外部结果未知持续时间、退款最终核对完成率。指标需要业务事件证据，不把模型调用成功或聊天结束当成解决问题。

初次真实试用应先跑通：授权找票 → 方案与来源 → 费用确认 → 上游受理 → 结果核对 → 异常有人负责。对每个环节同时定义允许办理、政策拒绝、信息不足、人工处理中、外部结果待核对、已完成等对用户可理解的状态。范围外订单明确退出边界，随后根据实际需求扩展。
