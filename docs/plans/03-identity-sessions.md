# M3：身份、授权与会话计划

状态：2026-09-20，首版已实现并进入逐项交付复核，实际覆盖见 [DELIVERY_AUDIT](../DELIVERY_AUDIT.md)。本文保留已确认设计与验收要求；当前实现、测试结果和未覆盖边界分别见 [DESIGN](../DESIGN.md)、[VALIDATION](../VALIDATION.md)，不以计划预期替代实际通过。

阶段约束：全部模块计划与整体复核完成前，不新增功能实现。参见 [总计划](../PLAN.md) 与 [M2 计划](02-business-rules.md)。

## 目标与用户预期

用户无需登录即可进行公开政策咨询；使用演示账户后，可以查询和办理本人或获得明确授权的客票。多人、多窗口、身份切换、授权撤销和请求重试不应导致越权、串单、串对话或误用旧确认。

身份认证回答当前操作者是谁；客票授权回答其可对哪些票执行哪些动作；业务资格与金额由 M2 计算；是否提交成功由 M4 的状态和记录证明。

## 已确认的 11 项决定

| 项目 | 已确认方案 |
|---|---|
| 演示登录 | 选择预置演示账户，后端关联模拟的身份及预订核验记录；明确标注演示，同时提供独立本地账号注册/密码登录；不做短信、实名或证件上传；保留替换真实认证的接口 |
| 游客使用 | 公开对话、简单政策咨询不强制登录；查看私有订单、报价、申请办理及相关结果前要求登录；聊天自报姓名不切换身份 |
| 授权粒度 | 按操作者、客票、动作判断，读多人订单只返回获授权部分及其金额；模型不接收完整未裁剪订单 |
| 代办 | 预置已核验记录，限定授权人、代理人、客票范围、动作、有效期、状态；可改签不自动赋予取消/退税权；查看限于授权任务必要信息 |
| 新授权及例外 | 新增授权、监护和争议进入模拟人工审核；申请不等于权限生效；不做完整授权管理后台，样例/测试可模拟生效、过期和撤销 |
| 多用户与多窗口 | 服务端维护登录会话，同一浏览器配置内多窗口共享身份、可以各开独立对话；不同用户通过独立浏览器配置/设备体验；换号后旧确认和迟到回复不能作用于新身份 |
| 历史与撤权 | 对话绑定账户，回放及供模型使用前检查权限；失效代办授权关联的会话停用其业务历史和上下文，新开对话继续本人业务；业务记录保留，查询仍受当前权限限制 |
| 退出与过期 | 服务端使当前登录会话失效；默认空闲 30 分钟、最长 8 小时，可配置；重新登录可查仍有权访问的完成记录，旧会话确认不能继续使用；使用服务端时间戳 |
| 确认绑定 | 具体报价、操作者、登录会话、对话、目标范围绑定；明确确认展示方案后由 M4 执行；换身份、范围或引用其他对话报价不能沿用旧确认 |
| 权限复核 | 查询、报价、确认、操作结果查询均校验；撤权/会话失效与最终提交的先后关系由 M3/M4 协调；已提交结果不因后来退出撤回 |
| 失败与最少展示 | 目标不存在或无权访问统一提示无法访问；前端、模型及普通执行记录仅取得必要字段，不包含完整证件、支付凭据或会话密钥 |

上述演示账户选择是作业的模拟身份入口，不构成真实身份核验。授权机制在该模拟身份前提下验证，不能把用户能选择另一个演示账户误称为生产账号安全验证已通过。

## 政策依据与范围

政策依据为三份 PDF §8、§8.1（p6）及 [资料核对](../knowledge/POLICY_GUIDE.md)：

- 成年具名旅客经身份及预订核验后办理本人客票；订单号、同姓、付款信息和主预订人身份不产生对其他成年旅客的权限。
- 代办需明确代理人、预订、动作的书面授权，并核验双方；本期只保存模拟核验结果及证据引用，不采集真实证件。
- 监护需人工核验，新增代办和争议不能由聊天声明自动批准。
- 代理商出票的退款渠道由 M2/M4 按政策路由，身份核验通过不改变退款渠道。
- 原支付方式和具名旅行额度的受益人不因代理人发起操作而改变；退款不能转入代理人账户。

首版仅公开咨询、演示身份、逐客票/动作授权、会话/历史隔离、可信确认与查询权限；不扩展企业组织权限、复杂家庭账户、代理授权自助后台或真实认证供应商集成。

## 内部模块与边界

| 子模块 | 负责内容 | 输出 |
|---|---|---|
| 身份及登录会话 | 演示登录、服务端操作者、会话有效性、退出/换号/过期 | 可信身份上下文或未登录/失效结果 |
| 客票授权 | 本人关系、预置代理关系、任务范围、当前有效性与必要字段 | 允许目标、动作及字段范围，依据/版本或拒绝原因 |
| 对话归属 | 对话的账户/游客归属、关联授权及业务历史访问 | 可以使用的对话范围或受限结果 |
| 确认校验 | 身份、会话、对话和报价范围的绑定校验 | 供 M4 最终复核的上下文；不直接修改订单 |

M3 不计算价格、不创建订单变更、不把审核申请变成授权。M5 管消息编排和上下文组装，M6 管页面与旧回复丢弃，M7 管审核/执行记录；它们均调用或遵守 M3 的访问约束。M4 的订单事实通过稳定客票/旅客标识与授权关系对应，不在 M3 中维护第二份订单真相。

## 输入、输出与逻辑数据

下列语义遵循共同契约；会话和授权持久化在 M4 同一业务 SQLite，身份服务使用 TypeScript。具体 schema 实施时细化。

| 数据 | 最小语义 |
|---|---|
| Actor / Traveler | 稳定账户和旅客标识、本人映射、模拟核验记录；姓名只用于展示和识别候选，不能作授权主键 |
| Authorization | 授权人/被代理旅客、操作者、预订/客票范围、动作、开始/到期时刻、状态、核验依据、版本 |
| Session | 随机会话凭据关联的服务端记录、操作者、创建/最近有效活动/最长到期、撤销状态及版本；原始凭据不出现在模型或日志 |
| Conversation | 游客会话或账户归属、依赖的授权/客票范围、业务上下文是否仍可使用；消息存储由 M5 设计 |
| ConfirmationContext | 报价标识及不可变内容引用、操作者、登录会话、对话、精确目标范围、服务端确认请求接收时刻 |

前端或模型可以提交目标选择，身份从服务端会话确定。工具参数中的账户/授权声明不得覆盖服务端值。

对受保护对象，鉴权失败不返回目标是否存在、他人姓名、同行列表、总金额或受限对象内容。公开政策与不涉及私有事实的计算说明不依赖旅客身份；使用用户假设值举例时须保持示例属性，不能生成可执行的真实订单报价。

逻辑结果区分需要登录、会话失效、无法访问目标、授权已变化、业务历史受限、确认绑定无效。只有目标已合法可见时，才提供该范围内的具体业务原因；内部原因标识供受限审核使用，不把未经授权目标的细节透出给前端或模型。

## 登录、退出与多窗口

服务端登录记录是身份依据；浏览器用 HttpOnly Cookie 携带随机会话凭据，同源写入口检查来源并实施跨站请求保护，具体配置与有效性测试在实施时完成。客户端身份标记只辅助页面丢弃旧响应，不作为服务端授权证据。

- 同一浏览器配置内多个窗口共享当前登录身份，但对话有各自标识和上下文。多人演示使用独立浏览器配置或设备；不同窗口不等于不同用户。
- 切换账户先使旧登录会话失效，再建立新会话；新身份不能继承旧身份业务历史、当前选票或确认。
- 请求开始时固定身份/会话/对话关联；返回时页面只接受仍与当前身份及对话一致的结果。M5 的长工具调用和流式输出也要处理身份或授权失效，不把旧任务重新绑定到新用户。
- 退出仅结束当前登录会话及其共享窗口，不删除其他独立登录会话、历史操作或业务账本；本期不增加“全部设备退出”功能。
- 空闲和绝对过期以服务端时间戳判断；普通页面刷新不改变身份，后台轮询不应无限续期。有效活动按主动用户交互记录，后台轮询/心跳不续期；M5 只流式发布进度，长调用结果发布前重查身份。
- 登录前仅公开咨询的对话可以保持体验连续，但不能借上下文继承身份、授权或私有订单事实；登录后新建账户对话，只复制已标记公共政策消息/来源，不迁移自由文本、私有目标或待操作意图；不允许传入别人的对话编号认领历史。
- 重新登录可以查询当前仍有权访问的操作记录；执行旧会话报价需重新获取符合当前事实的报价及确认。响应丢失后的查询恢复与重新执行业务必须分开。

## 授权与代办的最小实现

使用预置且可核对的关系记录，不建设通用权限平台：本人客票按本人核验关系授权；代理按当前有效且动作匹配的记录授权。有效期和状态由服务端检查，取消、独立退税、改签的权限不能互相暗中扩展。

改签代理可以取得完成改签所需的最少客票信息，但不自动取得该旅客全部历史、其他票或完整付款资料。多人操作只可包含每张票均获相应动作授权的目标；显式选中的目标中有不允许项时不能悄悄缩小范围执行。

新授权/监护/争议的申请可以由登录申请人发起，但只保存其主动提供的必要说明和待核验意图，不能因此读取或附带系统中的他人订单详情。创建核验申请不证明订单存在或权限成立。M7 必须支持此类“申请人可查询自己的申请状态、尚无目标业务权限”的情况。

代理商出票路由、政策例外、审核结论与授权是独立维度。审核单被记录、模型判断合理、持有支付信息都不构成新的操作权限。

## 撤权、历史与确认失效

每次使用私有数据前验证当前权限；报价生成时保存依据并不能代替提交时复核。失效授权不能继续用于新查询、新报价、旧确认或受保护操作详情查询。

按照已确认的最小方案，关联失效代理授权的会话停用其业务历史和上下文，不尝试在混合自然语言中逐句猜测哪些字可保留；用户可新开会话继续本人或其他仍获授权的业务。底层记录保留供受限审核，记录保留不等于允许原申请人无条件继续读取全部内容。

M5/M6/M7 需要维护足以检查上述依赖的关联标识，并在回放历史、准备模型上下文、输出工具结果/引用和查询记录时应用同一权限决定。不能只清空页面而继续把失效历史发给模型。

已经合法发送到用户设备的信息无法保证收回；本方案保证后续请求、回放及模型输入不再通过失效授权取得数据。重新获得授权也不能自动复用已失效的旧确认。

混合多人操作记录按当前可访问范围输出，不能用汇总金额或目标列表暴露已失权部分。按 C07 仅输出当前可见票的分项和小计，无法安全分离则详情整体受限，原始审计记录保留。

## 与 M4 的提交合同

M3 提供身份/权限规则和当前依据，M4 负责在最终提交中兑现：

- 报价和确认绑定操作者、登录会话、对话、动作和精确目标集合；模型不能构造 `confirmed: true` 跳过可信确认入口。
- 提交校验当前会话、授权状态与有效期，不能仅信任报价生成时的结论或缓存权限。
- 授权撤销、会话失效与订单提交置于同一业务数据库的写事务序列；M4 最终事务内读取当前会话/权限，并按最后资格检查时刻判断到期，事务内无外部等待。
- 如果有效提交先完成，随后退出或撤权不撤销已完成业务；如果失效先发生，旧请求不能再提交。在途请求的政策窗口仍使用首次完整有效接收时刻，但最终权限按 C03 的事务内判定点复核。
- 多人操作中任意目标失权，整笔确认不提交；可以让用户重新明确选择合法子集后重新报价。
- 完整授权确认请求的服务端接收时刻用于 M2 政策窗口；当前会话/授权是否仍有效另行检查。报价时间、客户端时间、数据库提交时间不能混作政策窗口依据。
- 幂等查询和重试仍检查权限；知道操作编号或幂等键不能读取别人的结果，也不能绕过撤权再次执行。
- 已完成操作可跨重新登录查询，但须满足当前访问权限；登录会话改变不产生第二次收费或退款。

## 验收方案

以下列出验收要求，当前结果和用例映射见交付复核；未覆盖项必须单列，不能把本表的预期当通过。服务端拒绝不能用页面隐藏控件替代。

| 场景 | 预期 |
|---|---|
| 游客政策咨询 | 无需登录得到公开答案；订单查询/报价/办理返回需要登录，无私有内容 |
| 本人客票 | 已验证身份读取本人票、获得合法报价；输入其他人的名字不更换操作者 |
| 多人订单的付款人 | 只能访问获授权部分；总价/目标列表不泄露未授权同行人；付款不赋权 |
| 代理动作矩阵 | 有效改签授权可做限定任务；不允许未授予的取消/独立退税，过期/未生效/撤销记录无效 |
| 核验申请 | 登录申请人能创建/查询自己的待核验申请，但不能凭工单号读取目标旅客订单或获得批准 |
| 多用户及对象编号替换 | 替换客票、对话、报价、操作、审核单编号均不能跨用户访问；模型或 skill 提交伪造身份无效 |
| 同账号多对话 | 上下文及待确认报价归属正确；另一段对话的报价不能在当前对话直接确认 |
| 换号及迟到回复 | 旧窗口不能提交旧报价；旧请求/流式输出不能进入新账号页面或上下文 |
| 退出/空闲/绝对过期 | 服务端失效，不受客户端改时钟影响；默认 30 分钟/8 小时边界前、等于、后验证；轮询不能无限续期 |
| 授权撤销与历史 | 停止关联业务历史回放和模型输入；页面、工具与普通日志均不继续泄露失权数据 |
| 撤权/退出与并发提交 | M4 用屏障等方式控制两种先后顺序；至多一次合法提交，无“检查通过后撤权仍写入”的窗口 |
| 响应丢失、重新登录 | 有权时恢复已完成结果，不重复操作；无权时不泄露记录内容 |

测试需查看工具返回、模型输入、页面状态和持久化结果；不能只断言回复中出现“无权限”。所有数据为虚构样例，生产身份安全不属于本轮验收承诺。

## 依赖与整体复核结果

| 依赖 | 已对齐的设计责任（尚待实现验证） |
|---|---|
| M2 | 只接受 M3/M4 提供的可信事实；权限失败不送入可执行金额报价；时间窗口与授权有效性分别核定 |
| M4 | 授权/会话与提交一致性、报价绑定、多人原子性、记录查询裁剪、幂等恢复、时钟与版本判定点 |
| M5 | 登录前后上下文归属、每轮身份绑定、失效历史过滤/停用、长调用和流式输出取消或丢弃 |
| M6 | 演示入口说明、必要时登录、多窗口切换、过期提示、报价确认及迟到回复处理 |
| M7 | 最少审核事实、申请人视角与目标权限区分、受限历史记录、脱敏 trace；不让审核记录成为越权入口 |
| M8 | 预置本人/代理/无权/失效身份与多人票、固定时钟、撤权竞态及权限矩阵验收 |

以上设计已由对应模块计划与共同契约承接，文档复核记录见 [PLAN_REVIEW](../PLAN_REVIEW.md)。保留已确认的 11 项产品决定；若实施发现需改变资金、时间或重要产品行为，再提出具体选项。
