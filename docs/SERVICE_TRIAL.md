# 本地服务试用

目的：让旅客在办理后知道“现在在哪一步、谁在处理、接下来做什么”，也让评审能操作异常路径。只围绕三份虚构PDF和样例订单；不接入真实航司、银行、身份核验、客服或外部通知，不扩充或猜测现实政策。

## 启动与身份

完成README的安装与构建后：

```sh
AIRLINE_SERVICE_TRIAL=1 AIRLINE_DB=var/service-demo.sqlite npm start
```

首次使用新库自动建立未来样例。重复启动保留记录，原作业模式默认不开启。当前数据库有待核对渠道结果时，关掉开关会拒绝启动，避免绕过保护。完整时间口径仍是UTC时间戳、五分钟报价、USD到分；金额算法未作更改。

旅客登录后左侧进入“我的服务中心”；客服在右上角“体验示例”中展开“模拟客服角色（本机演示）”，选客服1或2。模拟客服是可公开切换的本机测试身份，**不是生产员工认证**。可在两个独立浏览器会话中分别扮演旅客和客服；同一浏览器的两个标签共享登录身份，不适合同时扮演双方。

服务中心通过“刷新进度”读取最新记录，不宣称实时推送。聊天中可以问“退款到账了吗”“审核进展如何”，模型只查询当前旅客可见的状态；没有审批或写入回执工具。

## 五条可体验的流程

1. **找回样例票。** 注册个人账号 → 服务中心“找回样例客票” → 选择 `CANCEL-NSA-A` / `BHA-NEW-A` → 填写页面公开展示的演示验证码 → 选择只读或该票办理权限 → 提交。客服接单并核验后才建立授权。权限只覆盖申请票和动作，自申请起最长8小时，旅客可撤销；姓名、付款人自述和票号不直接赋权。验证码是公开虚构材料，不能复用为真实核验设计。
2. **办理到结果核对。** 例如取消初始的 `CANCEL-NSA-A`：先核对额度60美元、原路退税20美元及不退部分，明确确认后本地只登记一次。服务中心分别显示订单和退款任务，尚未收到回执时不显示银行到账。客服先受理并完成订单，再推进退款。可模拟回执丢失或失败 → 查询原请求并核对 → 模拟完成回执；整个过程不重复记账、不虚构到账时限。旧的作业操作没有渠道任务，不补造完成状态。
3. **人工往返。** 旅客创建咨询或已有例外审核 → 客服接单 → 请求补充非敏感说明 → 旅客回复 → 转模拟出票渠道 → 记录回复 → 答复或拒绝。两位客服竞争接同一单只会有一位成功。状态有时间线和责任角色；咨询关闭仍不等于退款获批，金额未知保持UNKNOWN/null。不要上传证件、病历、支付资料。
4. **按约束比较。** 用已授权代理身份，选择同一预订的 `NSA-A`、`NSA-B`，填写最高总补款和最后一段的最迟到达UTC时间。候选保持同行人同航班，并复用原费用规则；不自动放宽硬约束。最多检查256个完整组合、返回3个方案，只覆盖当前样例库、不宣称全网最优。选择后重新报价，另行确认并再次校验库存和版本。混合路线、复杂跨航司/联程明确不支持；不会猜测真实机场最短衔接时间。
5. **航变后的重新选择。** 客服展开“模拟新的航班变动”，给尚未起飞、尚无航变、没有待处理任务的自营样票增加一次180分钟延后事件。原起飞时间保留，票版本增加；旧报价拒绝执行。旅客在服务中心看到站内动态，重新查票核对适用航变选择，再独立确认。此事件只作用于选中的样票，不声称同步了一班真实航班的所有旅客。

## 实现与持久化

`ServiceDesk`负责核验申请、客服状态、渠道任务、站内动态和受约束候选查询。BookingService在同一SQLite事务中保存Operation、订单/账本和渠道任务；任务写入失败则整笔回滚。后续回执仅推进服务状态，事件、版本、防重结果原子保存。UNKNOWN/FAILED保持待接手，不盲目重提或回滚资金。

任务按当前逐票权限裁剪，不因多人共用Operation暴露他人的金额；撤权后相关历史会话冻结。工作台写操作经角色、同源/CSRF、版本、防重键检查；模型没有此类工具。当前界面只展示最近100条申请/动态和最多300条可见任务（未完成任务优先），未实现分页搜索与大规模队列调度。试用页面目前为中文。

## 与真实上线的差距

现在验证的是本地模拟工作流。仍需真实订单关系核验、员工权限、供应商签名回调与对账、实际退款/支付失败补偿、服务时限和超时升级、安全材料收集、真实航变订阅及外部通知。没有人工定价或批准金融例外入口；人工咨询结果不能覆盖原规则。额度的兑换、混合支付、跨承运人联程、附加服务履约及多节点运营仍不在范围。

验收记录见[当前验证](VALIDATION.md)；原作业和本次扩展分别报告，不将模拟回执当作生产能力。
