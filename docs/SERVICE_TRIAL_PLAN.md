# M9 本地服务试用计划

目标：旅客从授权找票、选择方案、确认办理，到查看渠道结果和异常接手，都有明确状态、责任者和下一步。保持原三份虚构政策、USD到分、UTC时间、明确确认、五分钟报价及并发防重约束。

本轮由用户授权尝试真实业务缺口的改进；实现可操作的本地模拟闭环，不接入真实航司、银行、身份核验、客服或通知供应商。新增 `AIRLINE_SERVICE_TRIAL=1` 显式开启，默认作业模式保留。两个模式都不真实扣款。工作台的身份切换只用于本机虚构数据演示，不是生产员工认证。

## 模块与边界

1. 服务范围与找票：限定DIRECT样例渠道。注册用户可提交指定样例订单的模拟核验申请；单独客服角色接单并核对演示验证码后，仅给申请客票、指定动作和既有8小时会话上限范围的授权。不凭姓名/付款人自述授予权限。外部出票渠道明确转办，不提供虚构外部联系方式。
2. 办理跟进：与本地Operation同事务建立按客票隔离的渠道处理任务。订单处理和原路退款分别记录；待受理/处理中/完成/失败/结果未知分开。完成依赖模拟渠道回执，重试与核对不产生第二笔账目；失败/未知有客服责任队列。历史旧操作仅标本地记录，不补造外部完成。
3. 人工服务：工作台与旅客端分开，接单、请求非敏感补充信息、回复、拒绝/转办都有时间线和版本防并发覆盖。金额未知保持未知；关闭咨询不等于批准退款。医疗证件等敏感原件不上传此演示。
4. 方案比较：在支持的相同路线/同一预订内，按用户明确选择的旅客、最后一段最迟到达时间及最高补款筛选少量完整方案，保持同行人相同航班。金额复用原规则，比较结果不锁座；最终仍重新报价、显式确认。不支持的复杂联程明确告知。
5. 航变与通知：模拟客服可提交有幂等键和版本的航变事件；更新客票事实、保留原始起飞时间、使旧报价失效。旅客在服务中心查看动态与下一步，提供重新查票/方案入口；不发送外部邮件或短信。

## 实现约束

新增状态和事件在SQLite中持久化，schema v2→v3原子升级，保留旧账户、订单和账本。客服写接口需独立角色、同源/CSRF、预期版本与请求幂等键；模型只有当前旅客权限下的进度查询能力，没有工作台或渠道回调工具。多人任务按当前逐票权限裁剪，不能因同一Operation泄露其他旅客金额。

在试用模式，存在未核对完成的渠道任务时不再次办理相关票；查询/恢复原结果仍可用。回执只更新进度，不重复退款/记账，也不在失败时擅自回滚金额未知的外部结果。

## 验收

- 游客/普通旅客不可直接执行客服动作；他人任务、失效授权、撤权后的消息均不泄露。
- 找票错误验证码/票号统一失败；重复申请和重复批准至多一组授权；不扩展到同行或其他订单；授权到期准确拒绝。
- Operation与渠道任务要么一起落库，要么全部回滚；未完成、未知、失败、成功及重新核对均可复现；退款必须等订单处理完成，重复回执不产生重复账目。
- 客服竞争接单、陈旧版本、请求重放、旅客补充信息、拒绝和转办分别验证，所有终态如实区分。
- 方案按预算和明确UTC截止时间筛选，无符合方案时说明原因；多人不拆散，不绕过权限/库存/政策。
- 航变重复回执只更新一次；旧报价确认失败；新方案仍需确认；消息只给有权旅客。
- 浏览器完整走一次找票、办理跟进和审核往返；全套原作业回归通过；真实模型单独验证进度查询，不把受控模型测试计作真实模型结果。
